# Electronics product, physical-unit receiving, packages and compatibility: release control

Status: **source implementation completed; production migration and end-to-end certification pending**.
Date: 2026-11-05. Applies to the existing 13 LEXA industries. This is not a new industry registration.

The reviewed seven-form policy snapshots are generated by `scripts/generate_electronics_wizard_snapshots.py`.
Run `--check` with the canonical contract validation before packaging.

## User workflows

1. **Products:** Existing category picker and AdaptiveProductFields resolve V2 family policy fields, variant axes, unit types and stock tracking. Pick a brand/model separately from merchant SKU. Setup cannot create opening stock.
2. **SKU matrix:** Preview sellable combinations, edit SKU/barcode/GTIN/prices, check conflicts, save atomically in a database transaction. No stock is created.
3. **Phones and feature phones:** Open the approved-opening scanner, choose the real warehouse, actual variant and actual primary IMEI. A device with one IMEI, even a two-SIM feature phone, is one physical unit. IMEI2 and further manufacturer-assigned IMEIs are optional. Scan drafts remain in browser memory until approved and posted. Purchases **must** use the existing purchase-order goods receipt, not the approved-opening endpoint.
4. **Other serialized electronics:** Capture manufacturer serial rather than inventing IMEI. A damaged physical unit is quarantined on receipt; it cannot be selected as available stock.
5. **Packages:** Define carton/pack base-unit conversion and schedule dated, immutable revisions. The purchase receiving API resolves the effective conversion as of the receipt timestamp. All prior receipts retain their historical quantities.
6. **Accessories:** Propose a device-model fitment. Inventory approver reviews kind (`physical`, `electrical`, `protocol`, `consumable`) with manufacturer/test evidence; electrical approvals require explicit safety confirmation. Revoked and legacy links are never implicitly recommended.
7. **Kits:** Create a sealed supplier kit or a draft assembled kit BOM. An approver activates. Quantity-tracked, non-lot, nonserialized components only; nested kits, cyclic kits and parent SKU variants are rejected. Assembly locks all relevant product rows, checks available unreserved stock in the warehouse, issues each component and receives exactly the assembled kit quantities in one serializable transaction. Reused idempotency keys return the existing result without additional movements.
8. **Search:** Product alias values link supplier SKUs, manufacturer codes, authentic GTINs, barcodes and brand aliases to the canonical merchant product. No stock is created.

## Design boundaries

- One unit may have 1..N registered identifiers. Identifiers do not each count as a unit.
- PostgreSQL trigger normalizes **all** newly registered serial units (purchase receiving and approved openings), checks IMEI Luhn, enforces globally unique claims within each tenant, and refuses to claim historical duplicates. Legacy conflicts are marked for human review, never arbitrarily mapped.
- Existing `Product`, `Category`, `StockMovement`, sales, invoices, credit notes, receipts, and IMEI references are not rewritten by this migration. No synthetic product rows are seeded.
- `inventory_receipt_batches` are idempotent, with row-locked and serializable posting. Ledger posting for approved opening is balanced. Kits only reclassify stock and component cost, not customer revenue.
- Tenant RLS is forced on all six new tables; new models are in `PrismaService` tenant-context delegate allowlist. Route decorators and OpenAPI are synchronized.
- Stock movement and exact-unit balance mismatches are **reported**, not silently corrected. Existing history remains auditable.
- Return, refund, sales, and physical delivery paths retain their existing guards. New exact-unit inspection and receipt routes do not bypass existing purchase-order authorization or open old imports.

## Staging release sequence (mandatory before production)

1. Record production release Git SHA, export a restorable **Neon** database snapshot/branch and verify backup manifest. Deploy new code first to **staging only**.
2. Apply the additive migration `20261105170000_inventory_receipts_identifiers_fitment_bundles` against the staging database using the direct, unpooled migration endpoint. Verify both the Prisma client/schema and RLS role grants.
3. Run `npm ci`, `npx prisma generate`, `npx prisma validate`, backend unit tests, `npm run contract:check`, backend `nest build`, then frontend `npm ci`, `npm test`, `npm run build`.
4. Confirm existing products, locations, categories, serials, purchase receipts, ledgers, and customer transactions retain IDs/counts. Query the legacy collision report before enabling scanner receiving.
5. Test 10 one-IMEI dual-SIM feature phones = **10** serials and **10** movements; 1 two-IMEI phone = **one** unit; same IMEI claimed twice fails. Test two simultaneous identical receipt submissions with the same idempotency key => one batch. Different payload same idempotency key => conflict.
6. Test serialized PO receiving and approved opening through their respective routes, wrong tenant/branch/variant, missing IMEI, invalid Luhn check digit, damaged quarantine and stock reconciliation.
7. Test 20 cartons x 10 cables = 200 base units; sell 35 => 165, including dated pack revision after original receipt. Old receiving values must not change.
8. Verify an accessory fit appears **only** if its model relation is currently verified with evidence, unrevoked and currently available in the selected branch and sellable variant. Unsafe electrical compatibility must not be recommended.
9. Define, approve and assemble a 2-component kit. Validate both component debits, single kit receipt, warehouse isolation, atomic rollback on insufficient stock, idempotency replay, and cost transfer.
10. Verify owner/storekeeper/cashier/approver permissions and cross-tenant negative cases. Run tenant-scoped RLS tests as `lexa_app_runtime`, not only privileged migrations. Check `platform_backup_inventory` includes all new authoritative tables.
11. Only after passing all tests, deploy backend (Render) and frontend (Vercel) from the same successful GitHub commit and promote the rehearsed migration to production with monitoring.

## Important release caveats

- A passing GitHub ZIP importer only proves source replacement and build steps; it does **not** prove a Neon migration or production deploy.
- The frontend scanning queue holds unsent IMEIs **in memory only** and does not persist personal device identifiers in browser storage. An offline draft is not stock; reload discards draft.
- Typed compatibility is intentionally conservative; existing model fits need reviewed manufacturer evidence before recommendation. A previous one-click verification endpoint returns a clear request to use the typed review route.
- Current kit assembly supports only unvarianted, quantity-tracked kit parents and quantity-tracked components. It fails closed for serialized/lot components instead of allocating them incorrectly. More advanced serialized kit assembly belongs in a separately tested release.
- `audit_electronics_stock_csv.py` is a read-only Python intelligence/quality tool, not an AI autoposter. It reports unsafe import lines without exposing full IMEIs and cannot mutate business stock.
